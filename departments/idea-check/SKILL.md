# 需要検証（アイデアチェック）

AI秘書のリサーチ部の仕事。アイデアごとに1つの記録ファイルを作り、段階を1つずつ進める。

```
node "$HOME/.claude/skills/secretary/scripts/secretary.mjs" <コマンド>
```

## 考え方（必ず守る）

1. **作る前に、安い方法から確かめる。** 一番高くつくのは「確かめる前に作り込むこと」。
2. **合格ラインは、始める前に書く。** 結果を見てから基準を甘くしない（作った時間が惜しくなる「もったいない」を防ぐ）。
3. **意見ではなく行動を見る。** 「欲しい」「いいね」は当てにならない。過去の行動、申込、毎日続けたか、お金を払ったかを見る。
4. **SNS の反応とアプリの需要を分ける。** 再生数やいいねが悪いのは、見せ方のせいのことが多い。ピボットを考えるのは、使い続けてもらえないとき。
5. **正直に試す。** まだ無いものを「ある」と見せない。申込を取るときは「開発を考えている案です」と明記する。架空の体験談、他社のアプリ名へのたとえ、PR 表記のない依頼投稿は使わない（マーケティング部の `RULES.md`）。
6. **個人情報は集めすぎない。** 申込は TestFlight の公開リンクや、名前の要らないフォームを優先する。話を聞いた人の名前は記録に書かず、「Aさん（30代・猫2匹）」のように書く。

## 段階（安い順）

| 段階 | やること | 分かること | 合格ラインの例 |
|---|---|---|---|
| 0 机の上 | 競合のレビュー（`review-insights`）、知恵袋や X の悩みの投稿、App Store の検索結果と競合の評価件数、検索キーワード（`keyword-research`） | 悩みが本当にあるか、競合がどれくらい使われているか、競合の不満 | 同じ悩みの声が10件以上ある。競合の不満に、自分の案の強みが当たる |
| 1 話を聞く | 対象の人5人に、過去の行動を聞く（`references/interview-guide.md`） | 悩みのために、今、手間やお金をかけているか | 5人中3人が、今その悩みに手間かお金をかけている |
| 2 案を見せて申込を取る | 画像1枚か15秒の動画で案を見せ、テスト版への参加や事前登録に誘う（`references/test-designs.md`） | 行動するほど欲しいか | 申込が◯人（先に決める。小さなアカウントなら20〜30人が目安） |
| 3 手作業で試す | アプリを作らず、人の手で同じ体験を届ける | 中心の体験が、毎日・毎週続くか | 2週目も半分以上が続けている |
| 4 最小の試作品 | 中心の機能だけのテスト版を、10人・10組ほどに使ってもらう | 使い続けるか | 2週後も半分以上が使っている |
| 5 公開 | ストアに出す | 知らない人も入れて、残るか、払うか | `bucket-check` と PM の判定の基準 |

- 段階は飛ばしてよい。ただし、飛ばした理由を記録に書く（例: 「競合が多く、段階0で悩みの大きさは確かめられた」）。
- 1つの段階は、長くても2週間で区切る。

## 手順

### A. 新しいアイデア（「〇〇のアプリを思いついた」）

1. `secretary.mjs status` を実行する。research 部署が無ければ、`dept add research` を提案する。
2. アイデアの言葉を整理し、足りないものだけ短く聞く。会話中なら聞き、定期実行なら聞かずに進める。
   - 誰の、どんな悩みか（ユーザーの言葉で）
   - 今その人は、どうやってしのいでいるか
   - 思いついたきっかけ
3. 記録ファイルを `departments/research/ideas/<アイデアID>.md` に作る（下の「記録の形」）。アイデアID は英小文字とハイフン（例 `voice-mimic-sns`）。
4. 段階0を、その場で進める。`review-insights` で競合を探し、ウェブで悩みの声を集める。
5. 段階0の結果と、段階1の計画（誰に、何を聞くか、合格ライン）を書く。
6. `secretary.mjs todo add "需要検証: <名前> 段階1（5人に話を聞く）"` を、ユーザーに確認してから入れる。

### B. 段階を進める（「話を聞いてきた」「申込が◯件」）

1. 記録ファイルを読む。
2. 結果を「結果ログ」に追記する。数・事実・相手の言葉（名前は書かない）を書く。
3. 合格ラインと比べて判断する。
   - 合格 → 次の段階の計画と合格ラインを書く
   - 不合格 → 「変える（対象・悩み・形を変えて、同じ段階をやり直す）」か「やめる」を提案する
4. 判断をユーザーと決めたら、`secretary.mjs decision add --title "<名前>: 段階N の判断" --decision "進む／変える／やめる" --reason "<数字と理由>"` で記録する。
5. 段階4に進むと決めたら、`departments/pm/projects/<アイデアID>.md` に開発のマイルストーンを作るよう提案する。

### C. 「アイデア一覧」「どれから手をつける？」

1. `departments/research/ideas/` の全ファイルを読む。
2. 表にする（名前・状態・段階・次にやること・最後の更新）。
3. 進める順番を、次の観点でおすすめする。
   - 次の段階が安く済むか
   - 悩みの強さ
   - ユーザーの得意分野（SNS で集めやすいか）
   - 今の主力アプリとの時間の取り合い

### D. 「ピボットすべき？」

- まず、どの数字が悪いのかを分ける。

| 悪い数字 | 変えるもの |
|---|---|
| SNS の反応 | 見せ方・チャネル |
| 申込 | 誰に・何を約束するか |
| 続けて使う人の割合 | 仕組み・対象 |
| 払う人の割合 | 料金・有料の中身 |

- 続けて使う人の割合が悪いときだけ、ピボットの候補を出す。その場合も、同じ対象（集めた人）に向けた変え方を優先する。

## 記録の形（`departments/research/ideas/<アイデアID>.md`）

```markdown
---
name: "<アイデアの名前>"
status: "検証中"        # 検証中 / 開発中 / 公開済み / 保留 / 不採用
stage: 0                # いまの段階（0〜5）
updated: "YYYY-MM-DD"
---

# <名前>

## 一言
（誰の、どんな悩みを、どう解決するか）

## 誰の・どんな悩みか
## 今どうしのいでいるか（代わりのもの）
## 一番あやしい仮説
（これが外れたら成り立たない、というもの）

## 段階ごとの計画と合格ライン（始める前に書く）
| 段階 | やること | 合格ライン | 期限 |
|---|---|---|---|

## 結果ログ
- YYYY-MM-DD 段階N: （事実・数・相手の言葉。名前は書かない）

## 判断
- YYYY-MM-DD: 進む／変える／やめる（理由）
```

状態や段階を変えたら、frontmatter の `status`・`stage`・`updated` も直す。

## AI の議論で考えるハーネスとの使い分け

[app-idea-feedback-harness](https://github.com/pcrito0901-source/app-idea-feedback-harness) は、複数の AI エージェントがアイデアを分析・反証し、BUILD / ITERATE / VALIDATE / PIVOT / KILL を判定して、外の世界で行う検証実験を設計する。役割は次のように分ける。

| | ハーネス | idea-check |
|---|---|---|
| 何をするか | AI どうしの議論で、案を**考える**・直す | 外の世界で**確かめた結果**を記録し、段階を進める |
| いつ | 段階0（机の上）と、案を変えるとき | 段階1〜5 |
| 残るもの | 分析と判定のレポート | `ideas/<ID>.md`（合格ライン・結果・判断） |

- ハーネスを使ったら、判定と、設計された検証実験を、記録ファイルの「結果ログ」と「段階ごとの計画と合格ライン」に写す。
- ハーネスの判定は AI の見立て。**進む・やめるの判断は、外の世界での結果（段階1以降）で決める。**
